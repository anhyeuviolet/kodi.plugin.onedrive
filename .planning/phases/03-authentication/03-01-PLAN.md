<objective>
The thin vertical slice this whole phase is built out from: one account, one device code, one
poll that comes back pending, one that comes back with a token, merged and written to disk and
read back — with no Kodi anywhere in the path.

Purpose: every remaining plan in this phase expands sideways from this slice. If the shape is
wrong — if the poll loop reads a 400 as a transport failure, if the merge drops a rotated refresh
token, if the write is not atomic — it is wrong here, after one commit, rather than after ten
layers have been built on it. The protocol itself is not a question: `SPIKE-DEVICE-CODE.md` ran
this exact flow three times against this project's own registration on two account classes, and
`.planning/research/verify_device_code.py` is a working stdlib implementation of it. What is being
established here is the shape the add-on will carry, not whether the protocol works.

This is a tracer, not a prototype. Every line is production code and stays.

Output: `resources/lib/auth/` with the protocol and the token store, and the test harness the
next four plans extend.
</objective>

    `device_code.py` carries four constants and three functions. The constants are the authority
    base, the embedded public client identifier `efe197b3-5c14-4d67-810f-e10406742a06`, the scope
    string exactly as `AUTH-04` locks it, and the two-member continue set. Put the authority in one
    constant for both account classes — the spike proved `/common` serves work/school and personal
    alike across three live runs, so there is no authority branch and no user-facing authority
    setting. Name the continue set `CONTINUE_ON` and give it exactly `authorization_pending` and
    `slow_down`, with the comment stating that it is an allow-list because Microsoft returns codes
    that appear in no reference, and a stop-list loops forever on the first one.

    `request_device_code(post, client_id)` posts the client identifier and the scope to the
    device-code endpoint and returns the parsed response. Read `verification_uri`, `expires_in` and
    `interval` from that response and never from a literal — the server returns
    `https://login.microsoft.com/device`, which is not the address most documentation cites, and
    `verification_uri_complete` is absent so a code can never travel inside the URL.

    `poll_once(post, client_id, device_code)` performs one token exchange and classifies the
    result into exactly one of: got a token, keep waiting, slow down, or terminal with this error
    code. A 400 status with a parseable JSON body is a protocol answer and must not be reachable by
    the exception path; that classification is the whole of `AUTH-10`.

    `read_identity_claims(id_token)` splits the compact serialization, pads the payload segment to
    a multiple of four and decodes it as URL-safe base64 into a dictionary, returning an empty
    dictionary on any failure. Return the claims as-is; the caller decides that `name` is the label
    and `sub` is the key. Put a comment on it stating that no signature is checked and no
    authorization decision may be taken from the result — trust comes from the TLS channel to the
    token endpoint, per D-01.

    `store.py` carries `read(path)`, `write(path, payload)` and `merge_token_response(previous,
    response)`. The write opens a temporary file in the target's own directory under a name carrying
    a fresh unique suffix, created exclusively at mode 0600, serializes, flushes, syncs the
    descriptor, then replaces the target in one call; on any exception it removes the temporary file
    and re-raises. Four details are load-bearing and each needs a comment naming its reason: the
    temporary file is a sibling of the target because a replace across mount points fails and the
    system temporary directory on Android is a different mount; the name is unique because two
    writers on a fixed name would collide; the sync precedes the replace because otherwise a power
    cut leaves a correctly-named empty file; and the mode is set at creation rather than adjusted
    afterwards because adjusting afterwards leaves a window at a wider mode.

    `merge_token_response` starts from the previous blob, overlays the response, and — this is the
    single highest-consequence rule in the phase — restores the previous refresh token when the
    response omitted one. Never the reverse. Set `date` from the current wall clock, because
    `oauth2.py` already computes expiry from it, and set `issued_at` to the same value so the
    inactivity clock is observable to the startup keepalive.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| token endpoint → add-on | Every field of the token and device-code responses is attacker-influenced if TLS is broken and server-controlled otherwise |
| add-on → profile filesystem | The refresh token is a ninety-day bearer credential written to a device other applications may share |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Information Disclosure | `store.write` | high | mitigate | Mode 0600 applied at creation, not adjusted afterwards, so no window exists at a wider mode |
| T-03-02 | Tampering | `store.write` | medium | mitigate | Sync before replace; the previous file stays valid until the rename lands, so a power cut cannot produce a validly-named empty credential file |
| T-03-03 | Elevation of Privilege | `read_identity_claims` | high | mitigate | Claims are decoded for display and local keying only; the module takes no authorization decision from them and validates no signature, and the comment says so at the definition |
| T-03-04 | Denial of Service | `poll_once` classification | medium | mitigate | Two-member allow-list plus the caller's expiry deadline; an undocumented error code terminates rather than looping |
| T-03-05 | Denial of Service | poll pacing | low | mitigate | The interval comes from the server response and the slow-down increase is permanent, so the client cannot self-throttle by polling faster than the endpoint permits |
| T-03-06 | Information Disclosure | test fixtures | medium | mitigate | The fake endpoint returns synthetic token values only; no live credential from the spike runs enters a tracked test file |
</threat_model>
