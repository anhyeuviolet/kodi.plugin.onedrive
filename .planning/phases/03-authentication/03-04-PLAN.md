<objective>
Make two simultaneous token refreshes impossible to lose data to, using the only mechanism that
actually excludes the two contenders this add-on has.

Purpose: the plugin and the background service are sub-interpreters inside one operating-system
process. That single fact eliminates both mechanisms a reviewer would reach for first, and it does
so silently — a record lock is granted to the second asker because a process cannot conflict with
itself, and then released for both when either closes a descriptor. An exclusive create asks the
filesystem whether a name already exists, and the filesystem does not care who is asking. The same
fact makes the textbook stale-lock breaker useless here, because the recorded process is always
alive.

The breaker is allowed to be imperfect, and that is deliberate: the next plan's adopt-the-winner
path is the backstop, and a breaker hardened past that point trades a rare double-refresh for a
common stall.

Output: the lock, its two-signal staleness test, and the per-account file layout.
</objective>

  <behavior>
    - Two threads in one process contend and serialise: the second acquires only after the first releases, and the sequence of entries and exits never interleaves
    - Two processes contend and serialise the same way
    - A lock file recording a different session identifier is stale immediately, with no waiting
    - A lock file whose modification time is older than the lifetime is stale
    - A lock file whose modification time is in the future is treated as unknown rather than as fresh, and becomes breakable rather than permanently unbreakable
    - A failed acquisition returns a false value rather than raising
  </behavior>
  <files>resources/lib/auth/lock.py, tests/test_refresh_lock.py</files>
  <action>
    Write the lock as a class taking the lock path, the current session identifier and a sleep
    function. The sleep function is injected because the only correct sleep inside Kodi is the one
    that reports a shutdown; in tests it is a callable that returns false immediately. The class
    imports nothing from Kodi.

    Acquire by opening the path write-only, create-exclusive, at mode 0600, and writing the session
    identifier into it as a small serialized record. On an already-exists error, ask the staleness
    test; if stale, break and retry the create; otherwise wait one short interval and retry until a
    deadline, then return a false value. Returning rather than raising is deliberate and needs a
    comment: losing the race is a normal outcome with a defined recovery, not an error condition.

    The staleness test answers two different questions with two different signals, and the comment
    should say which is which. Question one is "is the holder definitely gone" — answered by the
    session identifier: a lock recorded under a session other than the current one was left by a
    previous Kodi run and is stale with no waiting at all. Question two is "is the holder stuck" —
    answered only by time, and only within one session.

    For the age signal, read the lock file's own modification time and compare it against the current
    wall clock. Do not write a timestamp into the file and compare it against the reader's clock; the
    modification time puts one clock on both sides of the comparison and removes the question of
    whose clock is authoritative. A monotonic clock cannot be used at all here, because its origin is
    arbitrary per process and meaningless once written to a file that outlives one.

    Guard the negative age explicitly. A modification time in the future means the clock stepped
    backwards, which on a television box without a real-time clock is a normal boot event rather than
    an exotic one. Treat it as unknown: wait one interval and re-read; if it is still in the future,
    break it, because a permanently-future lock is otherwise unbreakable forever.

    Set the lifetime constant above the worst case of the request the lock protects, and state the
    arithmetic in a comment beside it. The transport at its defaults computes one hundred and
    fifty-five seconds; the refresh will be given its own short retry profile in plan 03-08 so that a
    lifetime around a minute is genuinely above its worst case, and the comment must name that
    dependency so nobody later restores the default profile without moving the constant. Offer a
    touch operation that refreshes the modification time for a holder that expects to outlive the
    lifetime — with the short profile it should never be needed, which is the point.

    Break race-safely: rename the stale file aside under a unique name, then retry the exclusive
    create. Whoever wins the recreate wins; the loser sees the already-exists error and waits. Delete
    the renamed-aside file afterwards, tolerating its absence. Add the comment that a residual double
    break is survivable because the next plan's adopt-the-winner path is the backstop — and say so in
    those words, because this is exactly the kind of reasoning a later reader "hardens" into a worse
    design.

    Release by closing the descriptor and unlinking, tolerating an already-removed file: someone may
    have broken it, and that is a case the design accepts rather than an error.

    Test the two-process case with the standard library's own process spawning, coordinating through
    files rather than through shared memory, and keep it fast — this suite runs in under two seconds
    today and a multi-second lock test would be the first thing anyone stops running.
