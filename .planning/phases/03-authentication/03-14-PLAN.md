<objective>
Run this on the television, and find out what the last three phases could not tell us.

Purpose: this is the first time the add-on runs on the hardware it exists for. Phase 1's acceptance
used an Android 11 emulator, one API level below this device, and that instrument was accepted for
exactly the questions it can answer — storage paths, file mode bits, exclusive create, loopback
binding — because those follow the API level rather than the form factor. Half of this phase's
criteria are the other kind: whether a code is readable from a sofa, whether the directional pad
reaches both buttons in a sensible order, whether the graphics stack renders the skin at all,
whether a fifteen-minute loop behaves on a low-end processor.

Three assumptions reach the television unresolved and this is where each is answered: that the
chosen font renders a nine-character code legibly at viewing distance; that releasing the plugin's
directory handle and re-entering as an action behaves as documented; and that the stock skin is the
active one, since font names resolve against whatever skin is running.

Output: an acceptance record with a verdict per row, written from what was seen.
</objective>

<task type="checkpoint:human-action" gate="blocking">
  <name>Task 1: Reach the television and install the archive</name>
  <what-built>
    An installable archive whose single top-level directory is named for this add-on's identity, built
    from the git index, produced by the build from plan 03-02.
  </what-built>
  <how-to-verify>
    1. Build the archive: run the build command and note the file it wrote.
    2. Enable developer options and network debugging on the TCL Android TV 12, and pair with it from
       this machine. This has never been driven from a recorded session — treat it as a step with its
       own outcome rather than as a preliminary.
    3. Get the archive onto the television, then install it from Kodi's own file manager rather than
       by pushing files into place. Installing through Kodi is the half of the packaging requirement
       no automated check can make, and pushing files bypasses exactly the code path being checked.
    4. Record: the television's Android version, the Kodi version, and **which skin is active**. Font
       names resolve against the active skin, so if it is not the stock skin, every font in the dialog
       may be substituting and the readability result means something different.
    5. If the television genuinely cannot be driven, stop and say so. Do not substitute a phone or the
       emulator and write it up as a television pass; record it as a stand-in run with the stand-in
       named and its limits stated.
  </how-to-verify>
  <resume-signal>Type "installed" with the Android version, the Kodi version and the active skin, or describe what blocked</resume-signal>
</task>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 2: The phase-1 checklist, repeated on the real device</name>
  <what-built>
    The same add-on that passed on an emulator, now on the hardware it was written for, plus a
    background service that performs a startup token refresh and must never prompt.
  </what-built>
  <how-to-verify>
    1. Open the add-on from the video, music and picture sections. Both entry points must load under
       this add-on's own identity.
    2. Confirm the background service starts at login.
    3. Reach all three dialogs — the code dialog and the two export dialogs — through the temporary
       dialog affordance, and confirm each renders from this add-on's own skin directory. If it does
       not appear in the action mapping, the routing change in plan 03-09 dropped it and the checklist
       is disarmed.
    4. Confirm two openings of the code dialog write two different image paths.
    5. Confirm no dialog appears over the home screen at boot. That is the observable form of the
       requirement that the background service never prompts.
    6. Pull the session log and sweep it for tracebacks; the count must be zero. Note that pulling an
       application-private log on this Android version needs the log copied to a public directory
       first, which phase 1 already recorded.
    7. Record anything the emulator could not have shown: rendering, timing, focus behaviour, anything
       that felt slow.
  </how-to-verify>
  <resume-signal>Type "approved" with each row's verdict, or describe what failed</resume-signal>
</task>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 3: Sign in from the sofa</name>
  <what-built>
    The device-code sign-in: a dedicated control for the code at a large font, a countdown driven once
    a second on a clock separate from the poll interval, a focused action on expiry that fetches a
    fresh code, a pattern image carrying only the provider's own address, and an account list with
    re-authorise and remove.
  </what-built>
  <how-to-verify>
    Sit where you would actually sit to watch something. Do not lean in.

    1. Choose the add-account row. Confirm the code dialog appears and that the container behind it is
       not left spinning — the row is supposed to release the plugin's directory handle and re-enter
       as an action, and a spinner outliving the dialog is how that assumption fails.
    2. **Read the code from your seat.** If you cannot, the requirement is not met: say so and name
       the font that should be tried instead. The layout names two smaller alternatives in a comment
       for exactly this.
    3. Watch the countdown for thirty seconds. It must tick every second, steadily, regardless of what
       the poll interval is doing.
    4. Scan the pattern image with a phone. Confirm it opens the same address the dialog shows, and
       that it does not contain the code.
    5. Enter the code on the phone and sign in with a work/school account. Confirm the dialog closes
       and one row appears in the account list, labelled with the account name and not with anything
       typed on the remote.
    6. Press back and confirm the account list is what it was.
    7. Start a second sign-in and press back or escape during it. Confirm no partial account is left
       behind — the list must be exactly as before.
    8. Start a third and let the code expire without entering it. Confirm the dialog shows the expired
       state, that the fresh-code action is **already focused** with no navigation, and that taking it
       produces a new code with its own countdown rather than resuming the old one.
    9. With the directional pad, move between the two buttons. Confirm the order is sensible and the
       initial focus is the intended one.
    10. Open the row's context menu and confirm re-authorise and remove are both present. Take
        re-authorise, complete it, and confirm a second account row was not created.
    11. Remove the account and confirm the row goes and the add-account row remains.
    12. Sweep the session log for tracebacks again; zero.

    Record the font that was actually in use and whether the readability verdict is a pass at that
    font. If the active skin is not the stock one, say so beside the verdict.
  </how-to-verify>
  <resume-signal>Type "approved" with the readability verdict and the font used, or describe what failed</resume-signal>
</task>
