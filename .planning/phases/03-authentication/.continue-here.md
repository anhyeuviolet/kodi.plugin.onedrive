## Open defects, none of them fixed

### `RefreshLock.release()` can report success having released nothing — REAL, unfixed

`resources/lib/auth/lock.py`. `release()` ends with `os.unlink` inside `except OSError: pass`.
Replaying the two-contender race 300 times: **~1 run in 10 the lock file still exists** the
instant `release()` returns. Capturing what the clause discards gives `PermissionError`
WinError 32 every time — the waiting contender in the same interpreter holds the file open, and
CPython on Windows opens without `FILE_SHARE_DELETE`. The lock is then orphaned for its full
90-second lifetime.

**The "flaky" lock test was never flaky.** The old note blamed runs over eight seconds. The
causality was backwards: failing runs are 7.98 / 8.45 / 8.73 / 8.51 / 8.38 / 8.66 / 8.47 against
a usual 3.2–4.3, the gap is **5.0 every time**, and 5.0 is the acquire timeout the loser burns.
The slow run *was* the failure. Disproved the old diagnosis by raising the deadlines to 30s —
it then failed at 30.1s at the same rate. That change was reverted rather than kept.

Windows-only in symptom: on Linux and Android `unlink` succeeds regardless of open handles, so
the guarantee holds on the TCL and **AUTH-14 stays checked**. The swallow is wrong everywhere,
and nothing asserts the lock file is gone after `release()` returns. Fixing it interacts with
the stale-lock breaker, so it is a design decision, not a patch.

## Critical Anti-Patterns

| Anti-pattern | Severity | What happened |
|---|---|---|
| Using a redactor as an equality test | blocking | The live-rotation check compared `refresh.fingerprint()` — eight characters, built for logs. Every Microsoft refresh token starts `1.AXEAuM`, so three different tokens compared equal and the run reported FAIL. **A PASS from that code would have been just as worthless**, and the phase would have recorded its highest-consequence requirement as proven on a check that never worked. Compare a digest of the whole value; a value chosen for one purpose does not transfer to another |
| `git checkout --` / `restore` / `stash` / `reset` to tidy the tree | blocking | Destroyed uncommitted work twice this phase — once a whole task's edits. Both times an executor treated the index as authority over a working tree that was ahead of it. Mutation helpers must hold their own bytes and assert their own restore by digest |
| Asking a source-text sweep to prove behaviour | blocking | Renaming `_is_secure_url` was caught by a text sweep, but **neutering the guard to `if True:` while keeping the name was not**. A sweep proves intent; only driving the code path proves behaviour. Two of 21 injected defects escaped 260 tests for exactly this reason |
| Marking a conjunction complete when one clause is unobserved | blocking | The requirements-marking step flips ids Complete even when later plans still declare them, and the shared-id gate does not fire. Caught by 03-05, then again in AUTH-06, AUTH-22, AUTH-20 and KODI-02. **Diff `REQUIREMENTS.md` before every commit that touches it** |
| Trusting a summary over the tree | high | 03-12 diffed the range instead of reading the input tables: the plans claimed 5 vendored files changed, the tree said 12 plus a skin, three had been silently converted CRLF→LF, and the error reporter had 8 call sites rather than the recorded 6 |
| Treating a negative observation as proof | high | "No dialog at boot" passes identically whether the service is running or never started. The premise still has no reading |
| Writing a manifest from memory | high | Four details of Kodi's repository extension would have been wrong from memory: `<dir>` is mandatory on Kodi 20+, `compressed=` and `zip=` are read by nothing, `checksum` needs `verify="sha256"` or nothing is verified, and `<hashes>true</hashes>` means MD5, which Kodi's own source calls broken |
