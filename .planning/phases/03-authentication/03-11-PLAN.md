<objective>
Convert the settings file to the schema that can express what this phase needs, add the one setting a
blocked tenant depends on, and take out the last two rows belonging to things that no longer exist.

Purpose: the expert-level requirement is not a styling preference — the element that declares a
setting's level exists only in the versioned schema, and this add-on's settings file still uses the
format that came before it. Written against the current file the requirement is unimplementable, so
either the requirement is restated or the schema is converted. The file is twenty-eight lines, this
phase edits it twice anyway, and the later phase that owns the schema would touch the same rows a
third time. Converting once is strictly cheaper (D-02).

The setting matters more than it looks. The tenant hosting this project's registration permits the
grant, so the message that points at this setting cannot be produced on demand and this setting is
the only thing standing between a blocked user and an add-on that simply does not work for them.

Output: a settings file in the current schema, with an escape hatch and without two dead rows.
</objective>

    - `tests/test_vendor_gates.py::test_string_ids_partitioned`, the reachability sweep — it reads setting labels from both the attribute form and the element form

  <action>
    Convert to the versioned schema: a version attribute on the root, sections containing categories
    containing groups containing settings. Carry every surviving setting across with its identifier,
    its label and its default unchanged — the identifiers are what stored values are keyed by, and
    changing one silently resets a user's choice.

    Translate the types to the names the new schema uses, give each setting the control declaration
    the new schema requires, and move each default into the form the schema expects. Keep the
    directory-listing default off. That default is a recorded deviation from upstream with a stated
    reason, its gate reads either schema on purpose, and a conversion that lost it would rearm an
    unauthenticated listener on a device where any installed application could reach it.

    Drop the two visibility conditions as part of the conversion rather than translating them. They
    test for a Kodi release older than this add-on's declared minimum, so they can never be false on
    any version that can install this add-on.

    Add the custom application identifier setting: empty by default, declared at the expert level, in
    a category where it reads as an escape hatch rather than as an ordinary option. Constrain its
    input to the identifier's shape where the schema allows, and note that the code validates it again
    before use — a settings-level constraint is a courtesy to the user, not the check.

    Convert the action row that clears the cache into the schema's action form. The gate asserting no
    row opens the module's own settings dialog reads an attribute that the new form does not have, so
    it stays green; note that in the summary so nobody later reads its greenness as untested.

    Leave the two directory-listing rows in place, converted. The subsystem behind them is deleted by
    a different phase's criterion, and removing only the settings would leave a listener running with
    no way to turn it off — strictly worse than either the current state or the intended one.
  </action>
