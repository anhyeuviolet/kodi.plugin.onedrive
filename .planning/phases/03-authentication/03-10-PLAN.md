<objective>
Keep the user signed in without ever asking them anything.

Purpose: the refresh token dies after ninety days of inactivity, and a media player is exactly the
kind of application that sits unused for months. A refresh at startup, well inside that window, is
what makes "stays signed in" true rather than aspirational. The constraint that shapes everything
else is that the background service may not prompt: it runs at boot, over whatever is on screen,
with no context for whatever it would ask. So it refreshes silently, and when it cannot, it records
a marker that the account list — built in the previous plan — renders as a row the user can choose
to act on.

The trap here is small and specific. A service starting at boot frequently has no network. Every
failure looks alike unless the code distinguishes them, and a transport failure that records the
marker produces a sign-in prompt after a router reboot.

Output: the startup check, wired into the service, provably unable to open a dialog.
</objective>

    - An account whose stored token was issued recently is skipped with no request at all
    - An account whose stored token was issued long ago is refreshed, and its stored refresh token afterwards differs
    - A transport failure leaves the record unchanged and records no marker
    - A provider grant failure records the marker on the record and leaves the token file alone
    - Two accounts are processed independently: one failing does not prevent the other from refreshing
    - Nothing in the module constructs a dialog

  <files>resources/lib/startup_refresh.py</files>
  <action>
    Write the check as a small module in this repository's own source rather than inside the vendored
    tree — it is new behaviour, not a modification to somebody else's file, and keeping it out of the
    vendored package keeps the modification record shorter. Note in the summary that the layering
    phase will move it under the Kodi-facing package it establishes; that move is a rename, not a
    redesign.

    Walk the account records. For each, read the stored blob and ask the threshold predicate from
    plan 03-07 whether a refresh is due. Skip when it is not — the common case must cost no request.
    When it is due, run the refresh through the same lock the plugin uses, because Kodi starting while
    the user opens the add-on immediately is not an exotic race, it is the ordinary one, and it is why
    the lock was built.

    Classify the outcome three ways. Success: nothing more to do. Transient: log it, leave the record
    untouched, and let the next start try again. Grant failure: write the marker onto the account
    record — on the record and not into the token file, because an unreadable token file is one of the
    failure modes being signalled and writing the marker into it would be writing into the thing that
    is broken. Optionally raise a non-modal notification, which is the only user-facing surface the
    service is permitted.

    Bound the whole attempt. A box starting at boot may have no route for some seconds; make a small
    number of tries with the shutdown-aware wait between them, and stop. A service that retries
    indefinitely is a service that is running when the user starts a film.

    Never construct a dialog, never prompt, and never use a wait that ignores the shutdown flag. The
    static assertion from plan 03-03 parses this module and everything the service imports from this
    repository, so a violation fails a test rather than surviving to a user's television.
  </action>
