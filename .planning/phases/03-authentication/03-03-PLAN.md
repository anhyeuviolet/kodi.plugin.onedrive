<objective>
Write the phase's instrument before the phase changes anything, and write down how to recreate the
one piece of this system that lives outside the repository.

Purpose: phase 1 established that a phase's gates are written first, in one file, red by
construction, with an owning plan named for each red assertion — and that the exclusion set is
defined once so it cannot drift. This phase needs a second gate file, and a second gate file that

read.

satisfied, but nothing in the repository says how the registration was made or how to remake it.
The tenant hosting it renews on activity; if it lapses, the embedded identifier stops working for
every installed copy simultaneously, including the television this phase's acceptance runs on.

Output: one harness module, one gate file covering every static assertion this phase owes, and the
registration runbook.
</objective>

    One file, written once, not edited again by any later plan in this phase. That constraint is what
    let phase 1's plans run in parallel without contending for the gate file, and it applies here for
    the same reason.

    Write these assertions:

    The scope assertion reads the scope constant out of the auth package's source and asserts it is
    exactly the locked set, then asserts by membership that it contains no broad-read form
    (Files.Read.All), no write permission and no application-wide grant form. Membership on a split,
    not equality on a whole string — the granted scope that comes back from the endpoint differs in
    ordering by account class, and a test written as equality will be rewritten wrongly by whoever
    hits that first.

    The forbidden-primitive sweep walks the syntax tree of every module under the auth package and
    fails on any import of fcntl or any construction of threading.Lock, reporting path and line. The
    requirement names both by name and the reason is in the research: the plugin and the service are
    sub-interpreters in one process, so a record lock cannot exclude them from each other and
    closing any descriptor releases the other's lock, while separate sub-interpreters hold separate
    lock objects. Carry a non-vacuity guard asserting at least one module under the package was
    visited.

    The broker sweep runs the harness's pattern scan for the setting name, the accessor name, the
    broker hostname and the broker path fragments, and asserts no hits. The two documents that are
    required to describe the old flow are already in the excluded set; pay for that with a positive
    assertion that both name the new flow, so the exclusion is not a hole.

    The expert-level assertion parses the settings file and asserts a custom client identifier
    setting exists, that its declared level is the expert value, and that its default is empty. Write
    it to read a level element rather than an attribute, since that element is what the versioned
    schema provides and is the whole reason the schema conversion was pulled into this phase (D-02).

    The service assertion parses the service entry point and everything it imports from this
    repository's own source, and fails on any construction of a dialog class or any call that opens
    one. The background service must never prompt; the requirement is unenforceable by review and
    trivial to enforce statically.

    The dispatch assertion parses the plugin router and fails if a method is looked up from a
    request parameter by dynamic attribute access. A plugin address is constructible from a
    favourite, a stored playlist entry or another add-on, so a dynamic lookup on a parameter is an
    arbitrary method call from an untrusted string. Assert positively that an explicit mapping
    exists and that it is non-empty.

    The redaction assertion asserts the transport layer's report builder covers the credential-shaped
    field names — the access token, the refresh token, the identity token, the device code and the
    user code — and that the error handler does not append a raw response body to the log.

    The runbook assertion belongs with the documents in the vendor gate file and was placed there in
    task 2; do not duplicate it here.

    Every sweep reports path and line, never a count. Every sweep carries a non-vacuity guard.

    Then record the gate state in the summary the way phase 1 did: a table of which assertions are
    green today, which are red by construction, and which plan owns each red one. A red assertion
    with no named owner is a gate nobody has agreed to satisfy.
  </action>
