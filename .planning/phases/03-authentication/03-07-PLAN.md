<objective>
Refresh a token without losing the rotated one, without signing anyone out over a race, and without
asking for a sign-in because the network was not up yet.

Purpose: the provider replaces the refresh token on every use and does not revoke the old one. Code
that keeps re-sending the original works perfectly until the original hits its ninety-day lifetime,
and then fails for every installation on the same day. It is invisible in development, invisible in a
two-week test cycle, and has no change to blame. The automated proof that the stored token changed is
therefore not a nice-to-have; it is the requirement.

The second half is the race. Kodi starts, the service begins a proactive refresh, and the user opens
the add-on immediately — this is the scenario the lock exists for, and it will happen. The loser must
re-read from disk and use what the winner wrote. It is also the backstop that lets the previous plan's
stale-lock breaker be imperfect on purpose.

Output: the refresh path, the adopt path, the startup threshold, and the tests that prove all three.
</objective>

  <behavior>
    - Two consecutive refreshes leave three distinct refresh tokens observed in sequence and the stored one equal to the newest
    - A response omitting a refresh token leaves the stored one in place and still advances the access token and the issue time
    - A contender that cannot acquire the lock waits, re-reads, sees a changed access token and returns it without performing an exchange
    - A contender that cannot acquire and re-reads an unchanged blob retries a bounded number of times rather than indefinitely

  <files>resources/lib/auth/refresh.py, tests/test_refresh.py</files>
  <action>
    Write the refresh as a function taking the store paths, the account key, a lock, a poster and a
    sleep function. Injection all the way down: no Kodi, no socket, no global state. The sleep
    function is the shutdown-aware wait in production and an immediate return in tests.

    The happy path is acquire, read the stored blob, exchange the refresh token, merge, write,
    release. Merge through the store's own merge so the keep-the-previous rule has exactly one
    implementation. Release in a finally block so a raised exchange does not leave the lock held for
    a whole lifetime.

    The loser path is the interesting one, and its order matters. On a failed acquire, wait briefly,
    then re-read the blob **from disk** rather than trusting anything loaded before the attempt. If
    the access token differs from the one held at entry, the winner finished: return it, no network
    call at all. If it is unchanged the winner may still be in flight, so retry a bounded number of
    times. Only when the lock is still held past its lifetime does the breaker come into play, and
    that belongs to the lock, not here.

    Give the exchange its own short retry profile — one or two attempts, no long backoff ladder —
    rather than inheriting the transport's default. The default's own comment computes a
    hundred-and-fifty-five-second worst case, and a lock lifetime above that would hold the other
    contender for minutes. A token refresh has no business sitting on that ladder: it has a defined
    recovery path, which is this file. Put the arithmetic in a comment next to the profile and name
    the lock's lifetime constant, so the two cannot be changed independently.

    For the rotation proof, drive the fake endpoint with two successive responses carrying different
    refresh tokens, run the refresh twice, and assert three values in sequence differ and that the
    stored one is the newest. Assert on what is on disk, not on a returned value — the requirement is
    about what was persisted, and a test that asserts a return value would pass against code that
    never wrote.

    If a log line is wanted to observe rotation in the field, log eight leading characters and no
    more, and say why in the comment.

  <name>Task 2: Tell a lost race apart from a dead grant, and a dead network apart from both</name>
  <behavior>
    - An invalid-grant response, with a store whose refresh token has changed since the attempt, yields the stored token and no re-authorisation signal
    - An invalid-grant response, with a store whose refresh token is byte-identical to the rejected one, yields a re-authorisation signal
    - A transport failure yields neither a re-authorisation signal nor a stored change, and reports itself as transient
    - The startup check skips a recently-issued blob and refreshes an old one
    - The startup check treats a missing issue time as old rather than as recent
  </behavior>
  <files>resources/lib/auth/refresh.py, tests/test_refresh.py</files>
  <action>
    Add the discrimination that makes the loser path safe in its second form: the contender raced
    through and performed its exchange before the winner wrote, and the provider answered that the
    grant is invalid because the token was already redeemed and rotated. Re-read the store. If the
    stored refresh token differs from the one just rejected, adopt it and return success. Only when
    the stored token is byte-identical to the rejected one is this a genuinely dead grant. Two
    fixtures, one where the store moved on and one where it did not, and the first must produce no
    re-authorisation prompt — that pair is the whole test for this requirement.

    Classify failures into three kinds and return which: succeeded, transient, and needs
    re-authorisation. Only a grant-level failure from the provider produces the third. A transport
    failure — no route, name resolution failure, timeout — produces the second and changes nothing on
    disk. Route the grant-level codes through the failure table from plan 03-05 so there is one place
    that knows what a provider code means, and note that the browse phase's requirement to
    distinguish failure states inherits this classification rather than inventing a second one.

    Add the startup check as a small predicate: given a stored blob and a threshold in days, should a
    refresh run. Refresh when the recorded issue time is older than the threshold, skip otherwise, and
    treat an absent issue time as old — a blob written before the field existed should be refreshed,
    not assumed fresh. Choose a threshold well inside the ninety-day window rather than at its edge,
    and state the arithmetic beside the constant. Refreshing on every start would also work and is
    simpler, but every write is a chance to leave a temporary file behind on a device that gets
    power-cut rather than shut down, so the threshold earns its complexity.
  </action>
