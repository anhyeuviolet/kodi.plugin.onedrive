<objective>
Close the two security findings this phase is responsible for: an interpreter that runs whatever
is in a database row, and a network call that can block forever.

Purpose: the key-value store this add-on's account manager writes through holds OAuth refresh
tokens, and it reads its rows back by evaluating them as Python source. The defence usually
offered — an attacker must already be able to write to your disk — is weaker on Android, where
the add-on's data directory resolves under a shared external storage path that older Android
versions expose to any application holding storage permission. Separately, the single outbound
HTTP call in the tree passes no timeout, so it inherits the global socket default of none: on
marginal Android TV Wi-Fi that is an unrecoverable hang behind a spinner with no way out.

The add-on id change is what makes the first of these a clean swap. There is no database from a
previous installation, so no mixed-format read path and no fallback evaluator is needed — write
JSON, read JSON, and let a malformed row raise.

Output: a store and a cache that serialize through JSON, and a request class with a named timeout
constant that Phase 4's central HTTP layer inherits.
</objective>

  <action>
    Exactly one outbound HTTP call site exists in the entire vendored tree: the URL-opening call
    inside the request class's retry loop. Everything else that looks network-shaped is inbound or
    unrelated — the service base class binds an ephemeral loopback socket to discover a port, both
    database modules open SQLite connections with a thirty-second timeout that is already bounded,
    and the source service logs a string containing the word timeout. This repository makes no
    direct HTTP calls of its own.

    Add a class-level constant named `HTTP_TIMEOUT_SECONDS` on the request class with the value
    `30`, and pass it as the `timeout` keyword at the call site. Use the named constant rather than
    a literal so Phase 4's central HTTP layer inherits one place to tune. Record the value and its
    reasoning in the SUMMARY for VENDORED.md, and flag it as unmeasured: research recommends a
    fifteen-to-thirty-second range for metadata calls without having measured anything, so the
    value is confirmed on the Android test phone during the acceptance pass in plan 01-07. Too low
    causes spurious failures on slow Wi-Fi; too high reproduces the hang the change exists to
    remove.

    The same call site is shared with the download path, which streams the response body to disk
    in fixed-size chunks. A single value is correct for both, because the timeout applies per
    socket operation rather than to a whole transfer — it bounds how long a single read may block,
    not how long a large file may take. State that in a comment at the constant, because the
    obvious objection to one constant serving both paths is that a large download would trip it,
    and it would not.

    Do not touch the retry loop's sleep. It goes through an injected wait function that defaults to
    the standard-library sleep; routing that through Kodi's abort-aware wait is Phase 4's job, and
    changing it here would be a behaviour change in a phase whose contract is preservation. Do
    record for VENDORED.md that the loop's worst-case wall time is the number of tries multiplied
    by the timeout plus the injected waits.
  </action>
