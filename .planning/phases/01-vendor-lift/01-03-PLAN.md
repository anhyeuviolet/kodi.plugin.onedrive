<objective>
Change what this add-on is before changing what it contains: a new id, a new name, a new
maintainer, a Kodi version floor that mechanically rejects Kodi 19, and a string-id namespace
that will not collide with the 89 ids arriving from the vendored module.

Purpose: the identity change is roughly ten lines and is independently verifiable, and landing
it first guarantees every later commit in the phase writes to a fresh, uncontaminated
`addon_data` directory. It also removes the need for a migration at all — a new id means a new
profile, so the original add-on is never read from or written to. The string renumbering rides
here rather than later for a hard ordering reason: the module's 89 ids collide completely with
this add-on's 26, and 22 of the 26 mean something different, so if the module's strings were
merged first there would exist a commit whose settings screen and context menus are silently
mislabelled.

Output: an `addon.xml` that Kodi 19 refuses and Kodi 20, 21 and 22 accept, a settings screen
whose actions drive this add-on rather than the original, and two `.po` files occupying the
30000 block with room for the module's 32000 block beside them.
</objective>

| Boundary | Description |
|----------|-------------|
| add-on id -> Kodi profile directory | The id selects which `addon_data` directory holds tokens, caches and databases |

| addon.xml import -> Kodi dependency resolver | The declared `xbmc.python` version is the only mechanism that can refuse installation on Kodi 19 |
